## Context

代码库是全新的：除 OpenSpec 脚手架、`pyproject.toml`（uv 锁定 Python 3.12.12）与 `.env.example` 外没有源码，不存在兼容负担。

产品形态已确认为**本地起 HTTP 服务、浏览器访问的工作台**，单用户、数据全部留在本机。这一条约束向下传导，决定了后面多数选择：不需要多租户、不需要分布式、不需要账号体系，也**排除了任何需要独立服务进程的重型 RAG 引擎**——它们要 Docker 全家桶和十几 GB 内存，与"本地跑一个工具"冲突。

动机见 `proposal.md - Why`，行为契约见 `specs/`。

调研中确认的两个外部事实，直接约束了设计：

- 试图自动搜索最优 RAG 配置的开源项目（Cognita、Verba 已归档，RAGBuilder、R2R 长期停更，AutoRAG 转型）已大面积退出。根因是实证搜索需要用户没有的评测集，且组合空间的重建成本过高。本设计因此选择**规则推荐**而非搜索。
- 能嵌入本地进程的 RAG 引擎实际只有纯 Python 库一类，其中值得接的只有 LightRAG（MIT，pip 依赖，但建索引需对每个 chunk 调 LLM 抽实体关系）。

## Goals / Non-Goals

**Goals:**
- 让不写代码的人完成从获取语料到验证效果的全流程，且每个决策点都能看到数据依据
- 让爬取、导入、处理、画像、建库、测试各段可独立重跑，中间产物落盘可检查
- 让语料来源（网页 / 本地文件）对下游完全透明，处理链路不分叉
- 使附件的原始地址从获取到答案全程可追溯
- 保持内核契约足够窄，使未来接入第二个实现不影响其他模块

**Non-Goals:**
- 不做多租户、账号体系与权限。单用户本地工具
- 不做桌面端打包（Electron / Tauri）。本次只做本地服务 + 浏览器
- 不做分布式、消息队列与横向扩容
- 不做实时爬取。更新靠用户触发或计划任务
- 不做实证式配置搜索，不承诺最优配置
- 不实现知识图谱检索。契约预留位置，界面置灰说明
- 不引入 RAG 编排框架（LangChain / LlamaIndex / Haystack 一类）。见 Decisions

## Decisions

### 交付形态：本地 HTTP 服务 + 浏览器

后端 FastAPI，前端单页应用，构建产物由后端静态托管。一条命令启动，打开 `localhost`。

理由：跨平台无需分别打包；前后端都是团队已有技术栈；调试最快；未来若要改成服务器部署，改动只是监听地址与鉴权。Electron / Tauri 的代价是要额外解决 Python 侧边车进程的打包与生命周期管理，收益只是一个原生窗口——现阶段不划算。

**默认只绑定回环地址**。对外监听必须显式配置，且启动时提示服务不含身份认证。

### 双入口，单一内部表示

网页爬取与本地导入在各自模块内完成获取，随后**产出结构相同的文档记录**：来源标识、标题、内容、内容哈希、获取时间、关联附件。区别仅在来源标识是 URL 还是本地路径。

下游的处理、画像、建库、检索**完全不区分来源**。这是让"学校爬网站"和"企业拖文件夹"共用一条流水线的关键，也避免了每加一种数据源就要改一遍下游。

**备选方案**：两条独立流水线。实现上更直接，但画像、建库、检索都要写两遍，且混合来源的知识库无法支持。

### 推荐器：规则式，不搜索

从画像的统计量出发，经一组**写死在代码里、可读可审的规则**得出建议，每条建议携带引用了具体统计数值的理由。

```
扫描件占比 > 阈值            → 建议启用 OCR
检测到高密度文号/编号模式    → 建议启用 BM25 混合检索
正文长度中位数 < 阈值        → 建议调小 chunk
重复模板占比 > 阈值          → 建议先去重
```

编号模式用正则族匹配常见的公文文号与表单编号形态，统计其密度——这是启发式，会有误判，所以产出的是建议而非决定。

与已退出市场的那批工具的区别是硬性的：**不跑评测、不搜索配置空间、不声称最优、每项可覆盖**。这三条写进了 `corpus-profiling` 的规格，是可验收的约束而非态度表述。

**刻意不做的一件事**：不从语料推断"用户会问什么类型的问题"。是否需要跨文档关联推理取决于查询而非文档，规格要求这类维度标记为"需使用者指定"，不给推断值。

### 不引入 RAG 编排框架

检索链路（切分 → 嵌入 → 向量与关键词双路检索 → 融合 → 可选 rerank → 截断与阈值过滤）**自行实现**，不引入 LangChain、LlamaIndex、Haystack 一类编排框架。

理由不是"框架不好"，而是本项目与框架的目标相反：**框架的价值在于把参数收进合理默认值、让使用者不必关心；而本工作台的全部价值在于把这些参数摊开、给出理由、让使用者逐项决定。** 框架每替我们藏起一个参数，我们都要再把它挖出来并保证覆盖生效——抽象在这里是负债而非资产。

次要理由：上述链路的实现量在数百行量级，框架节省有限，却引入其版本变更的传导风险与更深的调试路径。

**后悔权已由 KnowledgeKernel 契约提供**：契约只有三个方法，未来若改用某框架的检索实现，包一层适配器即可，`qa-service`、`workbench-ui` 与建库流程不受影响。因此现在不引入框架并非不可逆的承诺。

**边界的精确范围**：本决策只排除**编排框架**。单点能力库不受此限，且应优先选用成熟实现而非自写——向量存储、BM25、文档解析、中文分词、评测均属此类。判据是：**该库是否试图替我们决定链路如何编排**。

**备选方案**：以 LlamaIndex 或 Haystack 作为链路骨架。Haystack 的显式 DAG 与可视化配置形态最为接近，是其中唯一值得复评的；若链路复杂度显著超出预期（如引入多跳检索或 agentic 流程），应重新评估本决策。

### KnowledgeKernel：窄契约，首发一个实现

契约只有 `ingest` / `retrieve` / `delete` 三个方法，内核特有参数经配置透传，不进签名。

首发实现：**向量 + BM25 混合检索 + 可选 rerank**，向量用 Chroma persistent client，关键词用 BM25 库，两路结果融合后排序。

只做一个实现，但保留契约。理由：契约成本近乎为零（三个方法），而它让未来接图谱内核时不必改动 `qa-service`、`workbench-ui` 与建库流程。**现在就写第二个适配器才是过度设计**——LightRAG 的图谱能力对以单跳事实查询为主的语料是花钱买用不上的东西。

界面上把"知识图谱"选项置灰并写明原因，而不是隐藏——让用户知道这是有意为之的边界，不是遗漏。

### 混合检索是默认而非可选优化

纯向量检索对精确编号（文号、表单号、课程代码）召回极差，这是向量表示的固有短板，调参解决不了。而公文、制度、办事指南类语料恰恰编号密集。因此 BM25 通道是这类语料的**刚需**，推荐器会在检测到编号密度时主动建议开启。

### rerank 失败不静默降级

精排模型加载失败时中止并报错，而不是退回不精排。理由：静默降级会让用户以为自己在用精排配置评估效果，得到误导性的结论。宁可失败得明显。

### 索引版本指针

新版本写入独立目录 → 校验片段数非零 → 原子替换指针 → 保留上一版。重建期间检索走旧版本，失败或用户中断则原版本继续生效。

这同时满足了 `workbench-ui` 里"中断建库不破坏已有数据"的要求——中断只是让新版本目录成为孤儿，指针从未移动。

### 长任务：后台执行 + 进度轮询

爬取与建库在后台任务中运行，状态持久化到本地。浏览器只是查询进度的视图，关闭页面不影响任务，重开后恢复展示。

**备选方案**：请求内同步执行。实现简单，但一次爬取可能几十分钟，浏览器超时或用户误关页面就前功尽弃。

### 附件返回原始地址，不做代理

命中内容关联的附件，返回其原始 URL（爬取来源）或本地路径（导入来源）。下载的本地副本只用于文本解析，不对外暴露为下载端点。

理由：原始来源是权威的；代理会引入缓存一致性问题。代价是网站删文件后链接会失效——但让用户看到真实状态优于给出过期副本。

### 拒答在检索层

检索层按阈值过滤，命中为空时**不调用生成模型**，直接返回未找到。既省一次调用，也从结构上杜绝模型凭自身知识编造——比在 prompt 里叮嘱可靠得多。

测试界面在未命中时额外展示最接近的若干候选及其分值，帮助用户判断是阈值过高还是语料确实缺失。

### provider 抽象

`ChatProvider` 与 `EmbeddingProvider` 两个窄接口 + 按名注册表。OpenAI 与 DeepSeek **共用一个基于 OpenAI SDK 的实现**，差别只是 `base_url`、模型名与凭据变量。抽象层的价值在于容纳本地模型这种协议不同的实现。

**默认走云端 API**。本地嵌入（约 96MB）与本地 rerank（约 1.1GB）作为可选依赖，用户选择离线时才下载——不让所有人为可选能力付出安装体积。

### 存储布局

```
<data_root>/<kb_id>/
├── raw/            页面快照、导入文件副本、附件、元数据
├── profile.json    语料画像
├── config.yaml     该库的建库配置（含被人工覆盖的标记）
└── index/
    ├── current     指向生效版本
    └── <version>/  向量库 + BM25 索引
```

每个知识库一个目录，删除即删目录。无需数据库服务。

## Risks / Trade-offs

- **规则推荐给出次优建议** → 规格要求每条建议附带可核对的理由且可覆盖。用户能看懂依据就能判断是否采纳，这比一个不透明的"最优值"更可控。
- **网站改版使选择器失效，抽取悄悄变空** → `document-processing` 要求正文为空时标记失败而非放行；爬取结果摘要输出失败数，异常升高即可发现。
- **`scrapling` 相对小众，API 可能不稳** → 抓取与解析调用收敛在爬虫模块内，替换时影响面限于一个模块。
- **前端工作量被低估** → 三个界面是产品主体而非附属。任务拆分中前端独立成组，可先用最小可用界面跑通，再迭代交互。
- **本地服务被误开放到公网** → 默认绑定回环，对外监听需显式配置且启动时告警。规格中是可验收要求。
- **模型权重体积影响首次体验** → 默认云端，本地模型按需下载，界面上标明体积。
- **编号密度检测靠正则，会误判** → 只用于触发建议，不自动改配置；用户在界面上能看到检测到的样例。
- **DeepEval judge 的分值有波动** → 评测用于比较配置改动前后的相对变化，不把绝对分值当质量承诺。

## Migration Plan

全新项目，无数据迁移。分五阶段，每阶段有可独立验收的产物：

1. **骨架与 provider** —— 配置加载、provider 抽象与实现、本地服务骨架。验收：能跑通一次 chat 与一次 embedding 调用。
2. **语料获取** —— 站点分析、爬虫、本地导入、统一文档表示。验收：对一个真实站点和一个本地文件夹各产出 `raw/`。
3. **处理与画像** —— 正文提取、附件解析、切分、画像、推荐器。验收：产出画像与带理由的建议。
4. **内核与问答** —— KnowledgeKernel 契约、混合检索实现、rerank、问答组装、拒答、导出服务。验收：命令行下能提问并得到带引用与附件的答案。
5. **界面与测试** —— 三个界面、长任务进度、评测集与指标。验收：全流程可在浏览器中完成。

回滚：各阶段独立；索引层面的回滚由版本指针提供。

## Open Questions

- 前端框架与组件库的具体选型，在阶段 5 开始时确定。不影响后端契约与任务拆分。
- 首个样例站点用哪几个二级站点作为爬虫配置样例，在阶段 2 开始时确定。
- 计划任务的触发方式（系统 cron / 应用内调度）留待阶段 5，取决于界面上是否提供"定时更新"入口。
